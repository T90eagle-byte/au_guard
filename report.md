# Лабораторная работа №2. Модульная архитектура, интерфейсы и обработка ошибок

## 1. Архитектура приложения

Разработано приложение `au_guard`, состоящее из трёх внутренних пакетов:

- `internal/events` — структуры `Event` и `Decision`, проверка допустимости событий и типизированные ошибки.
- `internal/pipeline` — интерфейсы `EventSource`, `EventHandler`, источник `SliceSource` и обработчик `RuleHandler`.
- `internal/config` — конфигурационные параметры, значения по умолчанию и проверка их допустимых диапазонов.

Пакет `pipeline` зависит от `events`. Пакет `config` не зависит от других внутренних пакетов. Исполняемая часть `cmd/au-guard` связывает компоненты приложения. Циклических импортов нет.

## 2. Обработка событий

События передаются из `SliceSource` в `RuleHandler` через интерфейсы.

Для события `demo_2` с типом `file` и серьёзностью `7` источник возвращает структуру `Event`. Обработчик проверяет контекст, вызывает `Event.Validate()` и формирует решение `review` с причиной `high_severity`. Функция `process()` сериализует решение в JSON и записывает его в выходной поток.

После выдачи всех событий источник возвращает `io.EOF`, и цикл завершается успешно.

## 3. Обработка ошибок

Валидация использует сигнальную ошибку `ErrInvalidEvent` и тип `ValidationError`, позволяющий определить нарушенное поле.

Для сохранения причины ошибки обработчик применяет формат `%w`. Проверки `errors.Is` и `errors.As` позволяют распознать категорию ошибки и извлечь сведения о поле.

В ходе эксперимента замена `%w` на `%v` привела к ожидаемому провалу теста `TestRuleHandlerInvalidEvent`: текст ошибки сохранился, но цепочка причин была нарушена. После восстановления `%w` тест завершился успешно.

## 4. Проверка контрактов

Автоматическими тестами подтверждены:

- корректная последовательность выдачи событий и завершение через `io.EOF`;
- сохранение индекса источника при заранее отменённом контексте;
- отклонение недопустимых значений полей `Event`;
- соблюдение граничных значений конфигурации;
- распознавание ошибок через `errors.Is` и `errors.As`;
- отсутствие искусственного маркера пользовательского сообщения в тексте ошибки.

Тест `TestProcessReplaceableHandler` подтвердил возможность заменить штатный обработчик на `testHandler` без изменения функции `process()`. Выходные данные при этом сохранялись в `bytes.Buffer`, без использования терминала.

Тест `TestProcessEmptySource` подтвердил успешное завершение цикла без формирования выходных данных для пустого источника.

## 5. Итоговая проверка

Создан сценарий `scripts/check.sh`, который проверяет точную версию Go, форматирование, выполняет `go vet`, `go test` и сборку программы.

Сценарий успешно выполнил проверку четырёх пакетов. Собранная программа сформировала два решения:

```json
{"event_id":"demo_1","action":"observe","reason":"low_severity"}
{"event_id":"demo_2","action":"review","reason":"high_severity"}
```

Код завершения программы — `0`. Результаты проверки сохранены в `evidence/lab02/check.txt`, а решения — в `evidence/lab02/decisions.jsonl`.

Проверены контракты интерфейсов, граничные значения данных и сохранение причин ошибок. Автоматические тесты подтвердили заменяемость компонентов без изменения основного цикла обработки. Итоговая проверка и сборка приложения завершились успешно.
