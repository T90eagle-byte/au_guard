
# Архитектура au_guard

## 1. Назначение

`au_guard` — учебная система обработки событий безопасности на Go. Проект развивается последовательно: от модульной модели событий до конкурентной обработки и защищённой работы с файлами.

Основной интерфейс — CLI-команда `ingest`, принимающая события в формате JSONL и формирующая решения в том же формате.

## 2. Структура компонентов

| Пакет | Назначение |
|---|---|
| `internal/events` | Типы Event и Decision, валидация событий, ошибки |
| `internal/config` | Параметры приложения и их допустимые диапазоны |
| `internal/pipeline` | Источники событий, обработчики, конкурентный конвейер |
| `internal/cli` | Разбор аргументов, команды, коды завершения |
| `internal/providers` | Тестовая реализация интерфейса Model |
| `internal/tools` | Работа с артефактами, отчётами и SHA-256 |
| `cmd/au-guard` | Точка входа, сигналы и управление процессом |

## 3. Поток обработки событий

```text
Файл JSONL / stdin
        |
        v
    JSONLSource
        |
        v
      Producer
        |
        v
    jobs channel
        |
        v
  Worker pool (1–16)
        |
        v
   EventHandler
        |
        v
  results channel
        |
        v
    Coordinator
        |
        v
  JSONL в stdout
```

Дополнительно координатор собирает статистику обработки. Диагностика и статистика направляются в stderr, не нарушая формат машинного вывода.

## 4. Контракты интерфейсов

Интерфейс `EventSource` предоставляет метод `Next(context.Context)`, возвращающий очередное событие либо ошибку.

Интерфейс `EventHandler` получает событие и возвращает решение либо ошибку.

Такая архитектура позволяет заменять реализацию источника или обработчика без изменения остальных компонентов.

В проекте используются:

- `SliceSource` — источник событий из памяти;
- `JSONLSource` — потоковый источник JSONL;
- `RuleHandler` — обработчик с правилом на основе Severity.

## 5. Правило классификации

После успешной валидации события:

| Severity | Action | Reason |
|---|---|---|
| 0–6 | `observe` | `low_severity` |
| 7–10 | `review` | `high_severity` |

Решение содержит идентификатор события, действие и причину. Исходное поле Message в результат не переносится.

## 6. Конкурентный конвейер

Конвейер использует фиксированный набор работников (`worker pool`).

Producer читает события последовательно, назначает им индексы и направляет задания в ограниченную очередь.

Workers обрабатывают задания конкурентно. Результаты могут поступать в произвольном порядке.

Coordinator восстанавливает порядок по индексам и последовательно передаёт решения в выходной поток.

Для ограничения числа незавершённых операций используются `permits`.

Максимальное число одновременно находящихся в обработке, очередях и ожидании упорядоченной выдачи событий ограничено:

`workers + queue`

Это обеспечивает backpressure и предотвращает неограниченное накопление результатов при задержке раннего события.

### Закрытие каналов

- Producer закрывает `jobs`, когда больше не будет отправлять задания.
- Отдельная горутина закрывает `results` после завершения всех workers через `WaitGroup`.
- Coordinator дочитывает результаты и дожидается завершения управляемых горутин.

## 7. Отмена и штатная остановка

Отмена распространяется через `context.Context`.

На уровне точки входа используются `SIGINT` и `SIGTERM`. Для управляемых системных потоков stdin и stdout создаются дубликаты файловых дескрипторов, которые могут быть закрыты при остановке.

Так CLI может завершиться даже при незавершённом вводе либо заблокированном выводе.

Внедрённые через интерфейсы `io.Reader` и `io.Writer` потоки принадлежат вызывающему коду: функция CLI не закрывает их самостоятельно.

## 8. Безопасная работа с артефактами

`ArtifactReader` использует `os.Root` для ограничения файловых операций доверенным каталогом.

При чтении проверяются:

- допустимость относительного имени;
- отсутствие выхода за пределы корня;
- тип фактически открытого файла;
- ограничение размера 65 536 байт;
- состояние контекста.

Для чтения применяется ограничение `maxBytes + 1`, позволяющее обнаружить превышение лимита без молчаливого усечения.

Внутренние символические ссылки разрешены, внешние — отклоняются.

## 9. Формирование отчётов

Результаты анализа файлов публикуются в `report.json`.

Для защиты от частично записанного отчёта используется последовательность:

1. Создание временного файла в целевом каталоге.
2. Запись полного JSON.
3. Синхронизация и закрытие временного файла.
4. Атомарное переименование в `report.json`.

Файл создаётся с правами `0600`.

## 10. Запуск внешнего процесса

Компонент `hash_artifact` запускает только фиксированную утилиту `/usr/bin/sha256sum` с аргументом `-`.

При выполнении ограничиваются время, объём входных данных, stdout и stderr.

Команда запускается без shell, поэтому пользовательское имя артефакта не интерпретируется как команда оболочки.

Полученный SHA-256 проверяется, после чего метаданные могут быть добавлены в JSON-отчёт.

## 11. Границы безопасности

`au_guard` — учебный проект, а не промышленное средство защиты.

Применённые механизмы снижают отдельные риски, но не обеспечивают полную изоляцию процесса, защиту от всех изменений файловой системы или отсутствие всех возможных ошибок конкурентности.
